# Промпты ДЗ4

Промпты построены по шаблонам ДЗ2 ([prompt_templates.md](../hw2/prompt_templates.md),
структура **RTCF**: Role, Task, Context, Format). Общие правила (стек, стиль, запреты)
агент берёт из [CLAUDE.md](../../CLAUDE.md), поэтому в промптах на них ссылаемся по номерам.

Как шла работа: владелец продукта ставил задачу в чате («давай приступим к ДЗ4»),
AI-агент (Claude) разбивал её шаблоном №5 «Декомпозиция» на шаги задания и для каждого шага
формулировал рабочий промпт по шаблону. Ниже — эти промпты. Затем — набор
переиспользуемых промптов для частых проблем адаптивности и рефакторинга (результат занятия).

---

## Часть 1. Промпты по шагам

### 1. Декомпозиция ДЗ4 (шаблон 5)

```markdown
## Role
Ты — senior full-stack разработчик и тимлид проекта «Семейный бюджет» (правила CLAUDE.md).

## Task
Разбей ДЗ4 «Frontend-приложение с AI-агентом» на подзадачи так, чтобы после каждой
оставалось работающее приложение. Мок-данные вместо сервера, Supabase — в ДЗ5.

## Context
- ТЗ: docs/hw3/technical_specification.md (FR-3 операции, FR-4 отчёты, FR-5 период, FR-7 бюджеты)
- Дизайн: UI-концепция 4, макеты docs/hw3/ui_concepts/screens, токены design_tokens.md
- Критерии ДЗ: 8 шагов, ≥ 3 функции, ≥ 3 автотеста, адаптивность, отчёт development_report.md

## Format
Нумерованный список подзадач: что делаем → какие файлы → как проверяем.
```

### 2. Инициализация проекта (шаблон 1)

```markdown
## Role
Ты — senior frontend-разработчик (React + TypeScript), работающий по правилам CLAUDE.md.

## Task
Инициализируй проект в корне репозитория: Vite + React 19 + TypeScript strict,
Tailwind CSS v4 (плагин @tailwindcss/vite), React Router, Recharts, lucide-react,
Vitest + Testing Library + jsdom, ESLint (typescript-eslint strict) + Prettier.
Настрой алиас `@/` → `src/`, скрипты dev / build / test / lint / typecheck.

## Context
- Правила 5, 13, 16, 19: только согласованные библиотеки, Prettier 2/одинарные/100,
  запрет any и ts-ignore должен проверять линтер, запрет moment/lodash/axios — тоже.
- Версии — стабильные, опубликованные не позже чем за 2 недели (без «вчерашних» релизов).

## Format
package.json, vite.config.ts, tsconfig.*.json, eslint.config.js, .prettierrc, index.html —
каждый файл целиком. Затем `npm run build` и `npm test` с выводом.
```

### 3. Базовая структура и мок-сервер (шаблон 1)

```markdown
## Role
Ты — senior frontend-разработчик, проектирующий архитектуру под замену бэкенда.

## Task
Создай feature-based структуру (правило 6) и мок-бэкенд: данные выдуманной семьи
в памяти и localStorage, задержка ответа, имитация ошибок сети и 500.
Функции модулей `features/*/api` повторяют RPC из ТЗ §3.3 (list_transactions,
period_summary, report_by_category, budget_status, update_transaction с проверкой
updated_at …), чтобы в ДЗ5 заменить только реализацию.

## Context
- Модель данных — ТЗ §3.1, суммы в копейках (правило 7), даты строками (правило 8).
- Права ролей — матрица §3.2; «сервер» тоже проверяет права, а не только UI (правило 20).
- Демо-данные генерировать относительно сегодняшней даты детерминированно (правило 21).

## Format
План файлов → код → unit-тесты model/ (позитив, краевой случай, ошибка) → запуск тестов.
```

### 4. Экран «Операции» (шаблон 1, затем итерации)

```markdown
## Role
Ты — senior frontend-разработчик, верстающий по утверждённому макету.

## Task
Сделай экран «Операции» (FR-3.7 – FR-3.14): переключатель периода (месяц / свой цикл /
диапазон), сводка Доход / Расход / Остаток с полосой «Потрачено N% от дохода», поиск
с задержкой 300 мс, фильтры, история по дням с итогом дня, подгрузка порциями по 50.
Форма операции: нижний лист на телефоне, модальное окно на десктопе; ошибки после ухода
с поля и при сохранении, фокус на первое ошибочное поле; удаление с «Отменить» 5 секунд.

## Context
- Макеты: docs/hw3/ui_concepts/screens/operations_*.png, add_*.png
- Телефон < 1024 px — карточки и нижняя панель с «+», десктоп — таблица (ТЗ §4.8)
- Период, поиск и фильтры — в параметрах адреса (FR-3.14)
- Тексты ошибок — приложение B ТЗ; состояния — правило 14

## Format
Компоненты по одному в файле (правило 25), тесты Testing Library: позитив, пусто, ошибка.
```

Итерации по этому экрану шли короткими уточнениями, например:
«Скриншот 390 px: суммы в карточках сводки обрезаются многоточием. Найди причину
и предложи раскладку, при которой копейки видны и на 360 px» — см. отчёт, баг №1.

### 6. Тесты (шаблон 3)

```markdown
## Role
Ты — QA-инженер с опытом Vitest и Testing Library.

## Task
Покрой тестами: все функции model/ и shared/lib (позитив, краевой случай, ошибка),
API мок-сервера (идемпотентность создания, конфликт / нет прав / не найдена,
восстановление), экраны целиком: история, поиск, пустое состояние, ошибка 500 и «Повторить»,
форма (ошибки и фокус, сохранение с новым тегом, удаление и отмена), бюджеты, отчёты, права.

## Context
- Примеры из приложения C ТЗ — готовые тест-кейсы для периода и статуса бюджета.
- Время фиксировать: «сегодня» = 2026-10-17, подменять только Date, таймеры настоящие.
- Правило 22: тесты не ослабляем, чтобы «зазеленить».

## Format
Файлы `*.test.ts(x)` рядом с кодом, затем `npm test` с итогом.
```

### 7. Отладка по скриншоту (шаблон 4)

```markdown
## Role
Ты — frontend-разработчик, отлаживающий вёрстку по скриншоту.

## Task
На приложенном скриншоте {ширина} px {что не так}. Определи причину по коду
компонента и исправь. Объясни, почему ошибка возникала.

## Context
- Компонент: {путь}
- Ожидаемый вид: {макет / описание}
- Автопроверка: `scrollWidth - innerWidth` на 360 / 390 / 768 / 1024 / 1280 / 1440 px

## Format
Причина (1–2 предложения) → исправление → скриншот «после» на той же ширине.
```

```markdown
## Role
Ты — senior-разработчик, проводящий ревью перед сдачей.

## Task
Найди в src/ места, нарушающие правила 6, 11, 12 (длинные функции, логика в компонентах,
```

## Часть 2. Набор промптов для частых проблем

Готовые промпты: подставьте значения в `{…}` и приложите скриншот.

### Адаптивность

| № | Проблема | Промпт |
|---|---|---|
| A1 | Горизонтальная прокрутка на телефоне | «На {360} px у страницы {путь} есть горизонтальная прокрутка. Найди элементы, правый край которых больше ширины окна (`getBoundingClientRect().right > innerWidth`), объясни, какой из них задаёт ширину, и исправь без фиксированных ширин. Частые причины: элемент сетки или flex без `min-w-0`, `whitespace-nowrap`, фиксированная `width`.» |
| A2 | Текст обрезается многоточием | «На скриншоте {ширина} px текст {что} обрезается. Предложи раскладку, при которой он помещается целиком на 360 px, не уменьшая шрифт меньше 13 px: перенос блока на новую строку, другая сетка (`grid-cols-2` + `col-span-2`) или более короткая подпись.» |
| A3 | Разная раскладка телефона и десктопа | «Сделай {компонент}: до {1024} px — {карточки / нижняя панель}, начиная с {1024} — {таблица / верхняя панель}. Mobile-first: базовые классы для 360 px, затем `sm:` / `md:` / `lg:`. Скрывай вариант через `lg:hidden` / `hidden lg:block`, а не JS.» |
| A4 | Модальное окно на телефоне | «Окно {имя} на телефоне должно быть нижним листом на всю ширину с прокруткой содержимого и кнопкой «Сохранить», закреплённой снизу с учётом `safe-area-inset-bottom`; с 640 px — окно по центру. Проверь на 390×844 и 1280×900, что кнопка видна без прокрутки.» |
| A5 | Плавающая кнопка закрывает контент | «Кнопка «+» перекрывает последний элемент списка на {ширина} px. Добавь нижний отступ контейнеру не меньше высоты панели + safe-area, проверь прокруткой до конца.» |
| A6 | Проверка на всех ширинах | «Сними скриншоты страниц {список} на 360, 390, 768, 1024, 1280, 1440 px Playwright-скриптом, для каждой проверь `scrollWidth - innerWidth` и ошибки консоли, выведи сводку проблем.» |

### Рефакторинг

| № | Задача | Промпт |
|---|---|---|
| R1 | Длинный компонент | «Компонент {путь} длиннее 150 строк. Вынеси: состояние URL — в хук, загрузку — в хук `use{Имя}`, повторяющийся блок разметки — в отдельный компонент. Поведение не меняй, тесты должны пройти без изменений.» |
| R2 | Логика в компоненте | «Найди в {компонент} вычисления и ветвления по данным (классификация ошибок, расчёт сумм, фильтрация) и вынеси их в чистые функции `model/` с JSDoc и unit-тестами (правило 6).» |
| R3 | Производительность функции | «Измерь время {функция} на {5000} элементах до и после. Найди лишнее копирование (spread в цикле, `slice` в `reduce`), перепиши за один проход, сравни цифры.» |
| R4 | Размер сборки | «Покажи размеры чанков `vite build`. Предложи: ленивую загрузку тяжёлых страниц (`React.lazy`), отдельный чанк для react/react-dom/react-router, проверку, что тяжёлые библиотеки (Recharts) не попали в главный чанк.» |
| R5 | Подавление линтера | «Найди `eslint-disable`, `as`-приведения и `!` в {путь}. Для каждого предложи решение без подавления: стабильный ключ вместо зависимостей useMemo, сужение типа вместо приведения.» |
| R6 | Ревью по правилам | «Проверь изменения {коммит / файлы} на соответствие CLAUDE.md: правила 6, 7, 11, 12, 14, 16, 18. Таблица: правило — нарушение — файл:строка — исправление.» |
