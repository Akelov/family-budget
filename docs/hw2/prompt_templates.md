# Библиотека промпт-шаблонов (Шаг 3)

Все шаблоны построены по структуре **RTCF**:

- **Role (Роль):** кем выступает AI в этой задаче.
- **Task (Задача):** что конкретно нужно сделать.
- **Context (Контекст):** какая информация нужна агенту: файлы, типы, ограничения, примеры.
- **Format (Формат):** в каком виде нужен результат.

Значения в фигурных скобках `{...}` подставляются под конкретную задачу. Общие
правила проекта (стек, стиль, запреты) агент берёт из `CLAUDE.md`, поэтому
в шаблонах они не повторяются. Нужное правило достаточно упомянуть по номеру.

| № | Сценарий | Когда использовать |
|---|---|---|
| 1 | [Генерация компонента / функции](#1-генерация-компонента--функции-по-описанию) | Новая функциональность с нуля |
| 2 | [Рефакторинг](#2-рефакторинг-кода-с-улучшением) | Код работает, но плохо читается, дублируется или нарушает правила |
| 3 | [Написание тестов](#3-написание-тестов-для-существующего-кода) | Код есть, тестов нет или мало |
| 4 | [Исправление бага](#4-исправление-ошибок-и-багов) | Есть ошибка, сообщение консоли или неверное поведение |
| 5 | [Декомпозиция задачи](#5-декомпозиция-сложной-задачи-на-подзадачи) | Большая задача, которую нельзя сделать за один промпт |

## 1. Генерация компонента / функции по описанию

### Шаблон

```markdown
## Role
Ты — senior frontend-разработчик (React + TypeScript), работающий по правилам CLAUDE.md.

## Task
Создай {компонент | функцию | хук} `{Имя}`, который {что делает, 1–2 предложения}.
Требования:
- {требование 1}
- {требование 2}
- {поведение при ошибке / пустых данных}

## Context
- Где лежит: `{путь, напр. src/features/<фича>/components/}`
- Входные данные / типы: {интерфейс или ссылка на файл с типами}
- Связанные файлы: {что переиспользовать: formatMoney, Button, ...}
- Пример использования: {как его будут вызывать}

## Format
1. План: список файлов, которые создашь.
2. Каждый файл целиком в отдельном блоке кода с путём.
3. Тесты рядом с файлом: позитивный сценарий, краевой случай, ошибка.
4. Запусти тесты и покажи результат.
```

### Пример использования

```markdown
## Role
Ты — senior frontend-разработчик (React + TypeScript), работающий по правилам CLAUDE.md.

## Task
Создай компонент `BudgetProgress`, который показывает прогресс расходов по категории
относительно месячного лимита.
Требования:
- название категории, «потрачено из лимита» (например, «18 200 ₽ из 30 000 ₽») и полоса прогресса;
- цвет полосы: зелёный до 80%, жёлтый 80–100%, красный при превышении;
- при превышении — подпись «Превышение на 2 500 ₽»;
- если лимит не задан — показывать только сумму расходов без полосы.

## Context
- Где лежит: `src/features/budgets/components/`
- Входные данные: `interface BudgetProgressProps { category: string; spent: number; limit: number | null }`
- Связанные файлы: `formatMoney` из `src/shared/lib/format.ts`
- Пример использования: `<BudgetProgress category="Продукты" spent={18200} limit={30000} />`

## Format
1. План: список файлов, которые создашь.
2. Каждый файл целиком в отдельном блоке кода с путём.
3. Тесты рядом с файлом: позитивный сценарий, краевой случай, ошибка.
4. Запусти тесты и покажи результат.
```

**Почему это работает:** конкретные пороги (80%, 100%) и пример вывода («18 200 ₽ из
30 000 ₽») не оставляют агенту места для догадок. Пункт «лимит не задан» закрывает
краевой случай, который иначе обычно забывают.

## 2. Рефакторинг кода с улучшением

### Шаблон

```markdown
## Role
Ты — senior-разработчик, проводящий код-ревью и рефакторинг по правилам CLAUDE.md.

## Task
Отрефактори `{файл или функцию}`. Цель: {читаемость | убрать дублирование |
вынести логику из компонента | производительность | соответствие правилам}.
Поведение должно остаться прежним.

## Context
- Код: `{путь к файлу}` (или вставить код)
- Что не нравится: {конкретные проблемы}
- Что нельзя менять: {публичный API / пропсы / формат данных}
- Существующие тесты: `{путь}` — они должны проходить без изменений

## Format
1. Список найденных проблем (со ссылкой на номер правила CLAUDE.md, если нарушено).
2. Отрефакторенный код — файлы целиком.
3. Таблица «было → стало» по ключевым изменениям.
4. Результат прогона существующих тестов.
```

### Пример использования

```markdown
## Role
Ты — senior-разработчик, проводящий код-ревью и рефакторинг по правилам CLAUDE.md.

## Task
Отрефактори компонент `TransactionList`. Цель: вынести расчёт итогов из компонента
в чистые функции и убрать дублирование форматирования сумм.
Поведение должно остаться прежним.

## Context
- Код: `src/features/transactions/components/TransactionList.tsx`
- Что не нравится: внутри компонента считаются суммы доходов и расходов через
  `reduce` с `parseFloat`, суммы форматируются вручную через `toFixed(2) + ' ₽'`
  в трёх местах.
- Что нельзя менять: пропсы компонента (`transactions`, `onDelete`).
- Существующие тесты: `TransactionList.test.tsx` — должны проходить без изменений.

## Format
1. Список найденных проблем (со ссылкой на номер правила CLAUDE.md, если нарушено).
2. Отрефакторенный код — файлы целиком.
3. Таблица «было → стало» по ключевым изменениям.
4. Результат прогона существующих тестов.
```

**Почему это работает:** формулировка «что нельзя менять» и требование прогнать
старые тесты страхуют от того, что агент «улучшит» код, сломав поведение.

## 3. Написание тестов для существующего кода

### Шаблон

```markdown
## Role
Ты — QA-инженер / разработчик, пишущий автотесты на Vitest и Testing Library.

## Task
Напиши тесты для `{функция | компонент}` из `{путь}`.
Покрой:
- позитивные сценарии: {перечислить};
- краевые случаи: {пустые данные, нули, границы, большие числа, ...};
- ошибки: {некорректный ввод, исключения, состояние error}.
Код не меняй. Если найдёшь баг — опиши его отдельно, не исправляй.

## Context
- Тестируемый код: `{путь}`
- Тип данных / пропсы: {ссылка}
- Мок-данные: {где лежат или какие создать}
- Внешние зависимости, которые нужно замокать: {supabase, дата, ...}

## Format
1. Таблица тест-кейсов: «сценарий → вход → ожидаемый результат».
2. Файл тестов целиком (`{имя}.test.ts(x)` рядом с кодом).
3. Результат прогона.
4. Отдельно — найденные баги, если есть.
```

### Пример использования

```markdown
## Role
Ты — QA-инженер / разработчик, пишущий автотесты на Vitest и Testing Library.

## Task
Напиши тесты для функции `formatMoney` из `src/shared/lib/format.ts`.
Покрой:
- позитивные сценарии: целые суммы, суммы с копейками, суммы больше миллиона;
- краевые случаи: 0, отрицательное число, 0.1 + 0.2, очень большое число;
- ошибки: NaN, Infinity.
Код не меняй. Если найдёшь баг — опиши его отдельно, не исправляй.

## Context
- Тестируемый код: `src/shared/lib/format.ts`
- Особенность: Intl.NumberFormat для ru-RU использует неразрывные пробелы.
- Внешних зависимостей нет.

## Format
1. Таблица тест-кейсов: «сценарий → вход → ожидаемый результат».
2. Файл тестов целиком (`format.test.ts` рядом с кодом).
3. Результат прогона.
4. Отдельно — найденные баги, если есть.
```

**Почему это работает:** запрет менять код отделяет написание тестов от
исправления. Агент не «подгоняет» код под свои тесты, а честно сообщает о багах.

## 4. Исправление ошибок и багов

### Шаблон

```markdown
## Role
Ты — senior-разработчик, занимающийся отладкой. Сначала находишь причину, потом исправляешь.

## Task
Исправь баг: {краткое описание}.

## Context
- Где проявляется: {экран, компонент, функция}
- Шаги воспроизведения:
  1. {шаг}
  2. {шаг}
- Ожидаемое поведение: {что должно быть}
- Фактическое поведение: {что происходит}
- Ошибка из консоли / лог: ```{текст ошибки}```
- Скриншот: {приложить, если баг визуальный}
- Что уже пробовали: {если есть}

## Format
1. Причина бага (root cause) — 2–3 предложения.
2. Исправление — изменённые файлы целиком или diff.
3. Тест, который воспроизводит баг и теперь проходит (регрессионный).
4. Результат прогона всех тестов.
```

### Пример использования

```markdown
## Role
Ты — senior-разработчик, занимающийся отладкой. Сначала находишь причину, потом исправляешь.

## Task
Исправь баг: на мобильном сумма операции разбивается на несколько строк.

## Context
- Где проявляется: компонент `TransactionCard`, ширина экрана 360px
- Шаги воспроизведения:
  1. Открыть список операций на телефоне (или в DevTools, iPhone SE).
  2. Найти операцию с длинным комментарием.
- Ожидаемое поведение: сумма «−1 290,5 ₽» в одну строку справа.
- Фактическое поведение: сумма разбита на «−1 / 290,5 / ₽».
- Скриншот: screenshots/03_mobile_bug_before.png
- Что уже пробовали: ничего.

## Format
1. Причина бага (root cause) — 2–3 предложения.
2. Исправление — изменённые файлы целиком или diff.
3. Тест, который воспроизводит баг и теперь проходит (регрессионный).
4. Результат прогона всех тестов.
```

**Почему это работает:** требование сначала назвать причину не даёт агенту
лечить симптом. Регрессионный тест гарантирует, что баг не вернётся. Этот пример —
реальный баг из ДЗ1.

## 5. Декомпозиция сложной задачи на подзадачи

### Шаблон

```markdown
## Role
Ты — tech lead, планирующий реализацию фичи. На этом шаге код не пишешь.

## Task
Разбей задачу «{название фичи}» на подзадачи, каждую из которых можно выполнить
одним промптом и проверить отдельно.

## Context
- Описание фичи: {что должен получить пользователь}
- Где в архитектуре: {features/<имя>, model/, api/, components/}
- Что уже есть: {готовые функции, компоненты, таблицы}
- Ограничения: {сроки, без новых библиотек, ...}

## Format
1. Уточняющие вопросы, если что-то неясно (не больше 3), и допущения.
2. Нумерованный список подзадач (3–8). Для каждой:
   - что сделать;
   - какие файлы затрагивает;
   - критерий готовности (как проверить);
   - от каких подзадач зависит.
3. Порядок выполнения и что можно делать параллельно.
4. Риски и краевые случаи, о которых надо помнить.
```

### Пример использования

```markdown
## Role
Ты — tech lead, планирующий реализацию фичи. На этом шаге код не пишешь.

## Task
Разбей задачу «Месячные лимиты по категориям» на подзадачи, каждую из которых
можно выполнить одним промптом и проверить отдельно.

## Context
- Описание фичи: пользователь задаёт месячный лимит на категорию расходов
  («Продукты — 30 000 ₽») и видит, сколько потрачено, сколько осталось,
  превышен ли лимит и какой прогноз расходов до конца месяца.
- Где в архитектуре: features/budgets (model/, components/), данные — Supabase.
- Что уже есть: тип Transaction, formatMoney, компонент TransactionCard.
- Ограничения: без новых библиотек; сначала бизнес-логика, UI — потом.

## Format
1. Уточняющие вопросы, если что-то неясно (не больше 3), и допущения.
2. Нумерованный список подзадач (3–8). Для каждой:
   - что сделать;
   - какие файлы затрагивает;
   - критерий готовности (как проверить);
   - от каких подзадач зависит.
3. Порядок выполнения и что можно делать параллельно.
4. Риски и краевые случаи, о которых надо помнить.
```

**Почему это работает:** запрет писать код на этом шаге заставляет агента
сначала подумать. Критерий готовности у каждой подзадачи превращает план
в чек-лист. Этот шаблон — первый шаг цепочки в [prompt_methodology.md](prompt_methodology.md).
