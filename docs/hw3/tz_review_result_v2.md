## 2. Чего не хватает, чтобы AI-агент реализовал без уточняющих вопросов

- **Контракты API:** SQL/TS-типы параметров и ответов всех RPC, формат фильтров и курсора, суммы в копейках, таблица соответствия «код ошибки сервера → ключ из приложения B», включая все отказы `accept_invite`.
- **Схема адреса:** точный формат `period`, `mode` и каждого фильтра и правило, что важнее при конфликте с личным видом.
- **Архитектура клиента:** структура папок (`model/`, `shared/lib`, слой данных с заменой моков на Supabase для перехода ДЗ4 → ДЗ5) и выбор библиотек: кэш и повторы (TanStack Query или свои), формы, даты, виртуализация списка для NFR-3.2.
- **Дизайн:** раскладка для десктопа, палитра в HEX, отрисовка переключателя периода и диалога выбора диапазона, вид нижнего листа и модального окна.
- **Данные для ДЗ4:** мок-данные и фикстуры для тестов (семья, 3 роли, несколько сотен операций, архивные элементы, бюджеты в каждом статусе).
- **Настройка Supabase:** включено ли подтверждение email, Site URL и адреса возврата для `/invite/:token` и восстановления пароля, публикация Realtime с RLS, как создаётся тестовый проект и пользователи для NFR-G1 в CI.
- **Мелкие правила:**
  - поиск: экранирование `%` и `_`, минимальная длина запроса;
  - нижняя граница даты операции;
  - значение `period_start_day` в режиме `month`;
  - регистр дня недели в заголовке («Вторник» при том, что `Intl` даёт «вторник»);
  - можно ли менять тип категории или переносить подкатегорию в другую категорию.

## 3. Итоговая оценка готовности: **7 / 10**

Модель данных, права, расчёты периода и бюджета с тестовыми примерами проработаны хорошо (все примеры из приложения C я пересчитал, они верны). Но три места агент реализует по-своему: восстановление удалённой операции, разделение ошибок «нет прав» и «конфликт» и формат параметров адреса, а для части FR вообще нет критериев проверки.
