# Шаг 4. API

У приложения два вида API — оба даёт Supabase по адресу `https://<проект>.supabase.co/rest/v1/`.

## 1. Автоматический REST API по таблицам (PostgREST)

Supabase сам создаёт методы для каждой таблицы — без написания кода:

| Действие | Запрос | Пример |
|---|---|---|
| Прочитать (Read) | `GET /rest/v1/categories?select=*` | список категорий своей семьи |
| Создать (Create) | `POST /rest/v1/budgets` + JSON | новый бюджет |
| Изменить (Update) | `PATCH /rest/v1/categories?id=eq.<id>` + JSON | переименовать категорию |
| Удалить (Delete) | `DELETE /rest/v1/subcategories?id=eq.<id>` | удалить подкатегорию |

Что кому можно — решают правила RLS (шаг 5).

## 2. Серверные функции (RPC) — `POST /rest/v1/rpc/<функция>`

Файл: [supabase/migrations/20261017130000_api_functions.sql](../../supabase/migrations/20261017130000_api_functions.sql).

| Функция | Что делает | Требование ТЗ |
|---|---|---|
| `create_household(p_name)` | семья + вы владелец + 15 категорий и 42 подкатегории | FR-1.3 |
| `create_invite(p_role)` / `accept_invite(p_token)` | приглашение по ссылке и вход в семью | FR-1.4, FR-1.5 |
| `list_transactions(p_from, p_to, фильтры, p_offset, p_limit)` | история порциями по 50, поиск и фильтры | FR-3.8, FR-3.11, FR-3.12 |
| `period_summary(p_from, p_to, фильтры)` | доход, расход, остаток | FR-3.10 |
| `create_transaction(p_id, …, p_tags)` | новая операция; повтор с тем же id не создаёт дубль | FR-3.4 |
| `update_transaction(p_id, p_expected_updated_at, …)` | изменение с проверкой «не изменил ли кто-то другой» | FR-3.5 |
| `delete_transaction(p_id)` / `restore_transaction(p_id)` | удаление и «Отменить» | FR-3.6 |
| `report_by_category` / `report_by_subcategory` / `report_by_tag` | суммы для отчётов | FR-4 |
| `budget_status(p_from, p_to)` | сколько потрачено по каждому бюджету | FR-7.3 |

Суммы в ответах — в копейках (целые числа). Ошибки приходят с кодом, по которому сайт
показывает понятный текст: `P0401` — не выполнен вход, `P0403` — нет прав, `P0404` — не найдено,
`P0409` — операцию изменил другой участник, `23514` — неверные данные.

Функции записи работают с правами владельца базы (`SECURITY DEFINER`) и **сами проверяют**,
кто вызывает и что ему можно. Функции чтения работают с правами вызывающего — для них
действуют правила RLS. Вызывать функции могут только вошедшие пользователи.

## Проверка на локальной копии базы

[supabase/local/test_api.sql](../../supabase/local/test_api.sql) — сценарий на PostgreSQL 16:

| Проверка | Результат |
|---|---|
| Алексей создаёт семью | владелец «alexey», 15 категорий, 42 подкатегории |
| Операция 2 500,50 ₽ с тегами «Отпуск», «отпуск», «Дача» | создана; тегов 2 — «отпуск» распознан как существующий |
| Повтор с тем же id | возвращает ту же операцию, дубля нет |
| Поиск «дача» | находит операцию по тегу |
| Сводка | доход 9 500 000 коп., расход 250 050 коп., остаток 9 249 950 коп. |
| Изменение со старой версией | `Операция была изменена другим участником` (P0409) |
| Удаление и «Отменить» | операция исчезает из списка и возвращается |
| Бюджет «Авто» на вся категорию | потрачено 300 000 коп. из 2 000 000 |
| Мария по приглашению | становится участником |
| Мария удаляет операцию Алексея | `Недостаточно прав для этого действия` (P0403) |
| Повторное использование приглашения | `Приглашение недействительно` |
