# Шаг 8. Тестирование всех запросов к серверу

## Как проверяем

API проверяется на трёх уровнях:

| Уровень | Что проверяет | Где | Результат |
|---------|---------------|-----|-----------|
| 1. Unit-тесты сайта (Vitest) | перевод ответов и ошибок сервера, деньги, журнал | `npm test` | 25 файлов, 119 тестов ✅ |
| 2. Проверка API в базе (SQL) | каждая функция и таблица: норма, неверные данные, нет прав | [supabase/tests/endpoints_check.sql](../../supabase/tests/endpoints_check.sql) | 70 из 70 ✅ |
| 3. HTTP-запросы к серверу | что получает гость без входа по настоящему адресу API | `curl`, примеры ниже | все запросы отклонены ✅ |

## Уровень 2. Скрипт проверки API

Один файл, один запуск: **Supabase → SQL Editor → вставить файл → Run**. Тот же файл
работает и на локальной копии базы (`psql -f`).

Как он устроен:

- создаёт тестовых пользователей A (владелец), B (участник), C (владелец чужой семьи) и
  N (без семьи, потом администратор) — только мок-данные;
- вызывает запросы **от имени каждого из них** — так же, как это делает сайт: роль
  `authenticated` и id пользователя в `request.jwt.claims`; гость — роль `anon`;
- сравнивает результат с ожидаемым: `OK` или код ошибки;
- в конце **откатывает все изменения** — в базе не остаётся ни одной тестовой записи
  (проверено: после прогона в `auth.users` и `households` — 0 строк).

Для каждого запроса проверены три вида случаев: **нормальный** (данные сохраняются и
считаются верно), **неверные данные** (сумма 0, дата в будущем, чужая подкатегория,
повтор названия) и **нет прав** (гость, участник вместо владельца, человек из другой семьи).

### Что выяснилось при составлении тестов

Сначала проверки 3 и 59 ожидали ошибку `P0403` для пользователя без семьи, а сервер вернул
пустой список. Это не ошибка сервера, а неверное ожидание: функции **чтения** работают с
правами самого пользователя (`security invoker`), и правила RLS просто не отдают ему чужие
строки. Данные не утекают. Ожидание исправлено на «пустой список», а для **записи** после
выхода из семьи добавлена отдельная проверка 60 — она возвращает `P0403`.

## Уровень 3. HTTP-запросы гостя к настоящему серверу

Запросы с публичным ключом, но без входа — так API видит любой посторонний.
Ответы получены с сервера проекта 17.10.2026:

| Запрос | HTTP | Ответ сервера |
|--------|------|---------------|
| `GET /rest/v1/transactions?select=id` | 401 | `42501 permission denied for table transactions` |
| `GET /rest/v1/categories?select=name` | 401 | `42501 permission denied for table categories` |
| `GET /rest/v1/client_errors?select=id` | 401 | `42501 permission denied for table client_errors` |
| `POST /rest/v1/rpc/list_transactions` | 401 | `42501 permission denied for function list_transactions` |
| `POST /rest/v1/rpc/create_household` | 401 | `42501 permission denied for function create_household` |
| `GET /rest/v1/categories` с поддельным токеном | 401 | `PGRST301 JWT cryptographic operation failed` |
| `GET /auth/v1/health` | 200 | сервер авторизации работает |

Пример запроса (Windows PowerShell — `curl.exe`, macOS/Linux — `curl`):

```bash
curl "https://itijdbhguzsqggowfgbn.supabase.co/rest/v1/rpc/list_transactions" \
  -H "apikey: <публичный ключ sb_publishable_…>" \
  -H "Content-Type: application/json" \
  -d '{"p_from":"2026-10-01","p_to":"2026-10-17"}'
```

Ответ без входа: `{"code":"42501","message":"permission denied for function list_transactions"}`.
Сайт добавляет заголовок `Authorization: Bearer <токен входа>` — тогда тот же запрос
возвращает операции семьи вошедшего пользователя.

## Как повторить проверку

```bash
npm test                                         # уровень 1
bash supabase/local/run_all.sh                   # локальная база с миграциями
psql -h /tmp -p 54329 -U postgres -d fb -f supabase/tests/endpoints_check.sql   # уровень 2
```

На сервере: SQL Editor → содержимое `supabase/tests/endpoints_check.sql` → Run.
