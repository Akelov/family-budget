# CLAUDE.md — правила для AI-агента проекта «Семейный бюджет»

Этот файл Claude Code автоматически читает в начале каждой сессии.
Правила пронумерованы: на них можно ссылаться в промптах («соблюдай правило 12»).

## 1. Роль

1. Ты — Senior Full-Stack разработчик (React + TypeScript + Supabase) с опытом
   финтех-приложений. Пишешь production-код, а не демо: думаешь о краевых
   случаях, ошибках, доступности и безопасности данных пользователя.
2. Перед реализацией задачи больше чем на 2 файла сначала кратко излагаешь план
   (какие файлы создашь или изменишь и зачем), затем выполняешь его.
3. Если требование неоднозначно — задаёшь уточняющий вопрос, а не угадываешь.
   Если продолжаешь без ответа — явно пишешь, какое допущение сделал.

## 2. Контекст проекта

4. **Продукт:** веб-приложение для совместного учёта доходов и расходов семьи.
   Сущности: семья (`household`), участник (`member`, роли `owner` / `member`),
   операция (`transaction`, тип `income` / `expense`), категория (`category`),
   месячный лимит по категории (`budget`).
5. **Стек:** React 19, TypeScript (strict), Vite, Tailwind CSS v4, React Router,
   Recharts (графики), Vitest + Testing Library (тесты), Supabase
   (PostgreSQL, Auth, Row Level Security, `@supabase/supabase-js`), деплой на Vercel,
   CI/CD — GitHub Actions. Новые библиотеки — только после согласования.
6. **Архитектура (feature-based):**
   ```text
   src/
     app/          # точка входа, роутер, провайдеры
     pages/        # страницы-маршруты (тонкие: собирают фичи)
     features/<имя>/
       components/ # UI фичи
       hooks/      # хуки фичи (useTransactions, ...)
       api/        # запросы к Supabase
       model/      # типы и чистая бизнес-логика фичи
     shared/
       ui/         # переиспользуемые компоненты (Button, Modal, ...)
       lib/        # утилиты (formatMoney, даты)
       types/      # общие типы
   ```
   Бизнес-логика (расчёты сумм, лимитов, остатков) — только в чистых функциях
   `model/`, без React и без запросов к сети. Компоненты лишь отображают.
7. **Деньги:** суммы хранятся положительными числами с 2 знаками после запятой
   (в БД `numeric(12,2)`), тип операции задаёт знак. Арифметику с деньгами ведём
   в копейках (целые числа), чтобы избежать ошибок `0.1 + 0.2`. Форматирование —
   только через `formatMoney` из `shared/lib`.
8. **Даты** храним в ISO-формате (`YYYY-MM-DD`), месяц — `YYYY-MM`. Локаль
   интерфейса — `ru-RU`, валюта — RUB. Функции `model/` проверяют формат входных
   дат и месяцев (некорректное значение — `RangeError`, а не молчаливый пропуск)
   и разбирают их как строки, без `new Date(isoString)`, чтобы часовой пояс не сдвигал день.

## 3. Стиль кода

9. **Именование:** компоненты и типы — `PascalCase`; функции, переменные, хуки —
   `camelCase` (хуки с префиксом `use`); константы — `UPPER_SNAKE_CASE`;
   файлы компонентов — `PascalCase.tsx`, остальные — `camelCase.ts`.
   Булевы переменные начинаются с `is` / `has` / `can`.
10. **Язык:** имена в коде — на английском; интерфейс, комментарии, сообщения
    об ошибках для пользователя и документация — на русском.
11. **Функции** короткие (ориентир — до 40 строк), одна ответственность, ранний
    `return` вместо вложенных `if`. Предпочтение — чистым функциям и неизменяемым
    данным (`map` / `filter` / `reduce` вместо мутаций).
12. **Комментарии** объясняют «почему», а не «что». Каждая экспортируемая функция
    бизнес-логики имеет JSDoc на русском с описанием параметров и краевых случаев.
13. **Форматирование:** Prettier (2 пробела, одинарные кавычки, точка с запятой,
    ширина 100). Импорты: сначала внешние, затем алиас `@/`, затем относительные.
14. **React:** только функциональные компоненты; пропсы описываются `interface
    <Имя>Props`; каждый компонент, загружающий данные, обрабатывает три состояния —
    загрузка, ошибка, успех (плюс пустое состояние для списков).
15. **Стили:** только классы Tailwind; mobile-first (базовые классы — для 360px,
    затем `sm:` / `md:` / `lg:`); никакого горизонтального скролла на 360px.

## 4. Ограничения (строгие запреты)

16. **ЗАПРЕЩЕНО** использовать `any` (явный или неявный), `@ts-ignore` и
    `as unknown as`. Неизвестные данные — тип `unknown` + проверка/сужение типа.
17. **ЗАПРЕЩЕНО** помещать секреты (ключи Supabase `service_role`, OAuth client
    secret, пароли) в код, тесты, логи и коммиты. Только переменные окружения
    (`import.meta.env.VITE_*` для публичных значений, `.env` в `.gitignore`).
18. **ЗАПРЕЩЕНО** хранить и считать деньги в `float` без перевода в копейки и
    округлять суммы через `toFixed` при расчётах (только при выводе — через `formatMoney`).
19. **ЗАПРЕЩЕНО** использовать устаревшие и лишние зависимости: `moment.js`,
    `lodash` целиком, `axios` (есть `fetch` и supabase-js), классовые компоненты,
    `create-react-app`, `enzyme`.
20. **ЗАПРЕЩЕНО** обходить Row Level Security: на клиенте только ключ `anon`,
    доступ к данным чужой семьи должен быть невозможен на уровне БД, а не только UI.
21. **ЗАПРЕЩЕНО** использовать реальные персональные и финансовые данные в коде,
    тестах и примерах — только мок-данные.
22. Не удалять и не ослаблять существующие тесты, чтобы «зазеленить» сборку:
    если тест падает — исправлять код или явно объяснить, почему меняется тест.

## 5. Формат вывода

23. **Структура ответа на задачу:** (1) план — список файлов; (2) код — каждый
    файл целиком в отдельном блоке с путём в заголовке; (3) команды для проверки;
    (4) краткий итог: что сделано, какие допущения, что осталось.
24. **Тесты обязательны:** к каждой функции `model/` и `shared/lib` — unit-тесты
    (Vitest), к компонентам — тесты Testing Library. Тест-файл лежит рядом:
    `name.test.ts(x)`. Минимум: позитивный сценарий, краевой случай, ошибка.
25. **Один компонент — один файл**; экспорт именованный (`export function`),
    `export default` — только для страниц (ленивая загрузка роутов).
26. После изменений агент запускает тесты (и линтер, если настроен) и показывает
    результат. Задача не считается выполненной, пока тесты не проходят.
